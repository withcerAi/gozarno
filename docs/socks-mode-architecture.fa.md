# معماری حالت SOCKS مستقل در Gozarno VPN

وضعیت: پیش‌نمایش پیاده‌سازی شده است؛ جزئیات و محدودیت‌های واقعی در docs/socks-mode.md آمده است. این سند طرح اولیه را نگه می‌دارد. موتور فعلی در ترد موجود برنامه اجرا می‌شود، فقط IPv4 دارد و استثنای فایروال LAN را خودکار ایجاد نمی‌کند.

## قرارداد اصلی

وصل، قطع، reconnect و crash موتور SOCKS نباید route، DNS، proxy سیستم، MTU کارت فیزیکی یا firewall خروجی عمومی ویندوز را تغییر دهد. اتصال TCP/UDP بازی‌ای که مستقیم باز شده باید همان مسیر و socket را نگه دارد. ازدحام لینک مشترک یا قطع واقعی اینترنت خارج از این قرارداد است.

## مسیر داده

بازی و برنامه‌های مستقیم → پشته شبکه ویندوز → اینترنت مستقیم

برنامه‌های تنظیم‌شده برای SOCKS → listener محلی → SocksSession → پشته TCP/UDP در فضای کاربر → PacketTransport → OpenConnect CSTP/DTLS → سرور VPN

اتصال بیرونی OpenConnect یک socket معمولی روی اینترنت مستقیم است. بسته‌های داخلی پروکسی وارد جدول مسیریابی ویندوز نمی‌شوند. VPN عادی و SOCKS مستقل دو backend مجزا هستند؛ هنگام فعال بودن یکی، تغییر حالت با قطع همان session انجام می‌شود. تبدیل یک VPN سراسریِ ازقبل‌متصل به SOCKS مشمول تضمین عدم تغییر مسیر نیست.

## محدودیت واقعی هسته فعلی

در src/vpninfo.cpp مسیر فعلی setup_tun_vfn → openconnect_setup_tun_device → vpnc-script → VpnRoutes::apply است. این مسیر برای SOCKS مستقل استفاده نمی‌شود. حتی حذف routeها بعد از اجرای script یک بازه اختلال ایجاد می‌کند و پذیرفته نیست.

SocksBridge فعلی برای AppRouter است؛ socketهای خروجی را به آداپتور ویندوز pin می‌کند و نام‌ها را با QHostInfo حل می‌کند. تغییر listen address به‌تنهایی جداسازی مورد نیاز را فراهم نمی‌کند. این bridge برای routing قبلی حفظ می‌شود و SocksFrontend مستقل ساخته می‌شود.

هدر OpenConnect تابع openconnect_setup_tun_fd را دارد، اما پیاده‌سازی ویندوز در .tools/openconnect/tun-win32.c عملیات TAP DeviceIoControl انجام می‌دهد. بنابراین نمی‌توان یک pipe معمولی را بدون تغییر backend به آن داد. برای مسیر مستقل باید packet-I/O داخلی OpenConnect توسعه داده شود و فقط در حالت SOCKS از آن استفاده شود. هیچ fallback خودکاری به TUN یا script مجاز نیست.

## اجزا

- SocksModeController: مالک چرخه عمر، تنظیمات ثابت هر session، وضعیت و خطاها؛ مستقل از VpnRoutes، AppRouter، KillSwitch، GamingSession و NetworkEvents بازیابی آداپتور.
- SocksWorker: فرایند جدا، با IPC محلی محدود به کاربر جاری؛ crash آن فقط sessionهای پروکسی را می‌بندد. خروج برنامه باید worker را با Windows Job Object خاتمه دهد؛ secrets در آرگومان command line قرار نمی‌گیرند.
- SocksFrontend: SOCKS5 CONNECT و UDP ASSOCIATE؛ پاسخ موفق CONNECT پس از برقراری واقعی مقصد؛ DNS نام مقصد درون تونل؛ بدون تغییر proxy ویندوز.
- UserSpaceStack: پشته TCP/UDP مستقل با آدرس تخصیص‌یافته سرور، MTU داخلی، timer، retransmission و IPv4/IPv6. گزینه اولیه lwIP است؛ انتخاب و بسته‌بندی نهایی پس از نمونه فنی، بررسی مجوز و تست ویندوز قطعی می‌شود. TCP یا رمزنگاری اختصاصی از صفر نوشته نمی‌شود.
- PacketTransport: صف محدود بسته‌های IP بین پشته و OpenConnect، اعلان wakeup قابل لغو، حفظ مرز بسته‌ها، backpressure و teardown قابل پیش‌بینی؛ هیچ API تنظیم شبکه سیستم در این ماژول وجود ندارد.
- TunnelDnsResolver: درخواست DNS از طریق پشته داخلی به DNS سرور VPN؛ در نبود DNS قابل استفاده، resolver مشخص‌شده برای همان session از داخل تونل. هرگز fallback به resolver ویندوز برای مقصد SOCKS ندارد. DNS نام خود gateway برای برقراری اتصال بیرونی می‌تواند از اینترنت مستقیم استفاده کند.
- SessionRecovery: reconnect فقط داخل worker؛ در خرابی تونل، ارتباطات پروکسی بسته یا متوقف می‌شوند و به اینترنت مستقیم fallback نمی‌کنند. بازگشت اتصال، socketهای ازبین‌رفته را زنده نمی‌کند؛ برنامه مصرف‌کننده باید دوباره وصل شود.

## تنظیمات و رابط

- انتخاب حالت: VPN معمولی / SOCKS مستقل؛ هنگام اتصال قابل تغییر نیست.
- پورت قابل انتخاب، پیش‌فرض 1080؛ تعارض پورت خطا می‌دهد و برنامه پورت دیگری را بی‌خبر جایگزین نمی‌کند.
- پیش‌فرض listen فقط 127.0.0.1؛ نمایش آدرس و پورت با دکمه کپی.
- تیک «اشتراک در شبکه محلی (LAN)»، پیش‌فرض خاموش؛ انتخاب کارت فیزیکی و bind روی IPv4 همان کارت، همراه با loopback؛ آدرس 0.0.0.0 به کاربر به عنوان آدرس اتصال نمایش داده نمی‌شود.
- اشتراک LAN نیازمند نام کاربری و رمز اختصاصی پروکسی است؛ رمز VPN برای آن استفاده نمی‌شود. رمز ذخیره‌شده با DPAPI حفاظت می‌شود؛ در لاگ و diagnostic قرار نمی‌گیرد. روی loopback احراز هویت می‌تواند اختیاری باشد.
- فقط peerهای همان subnet مجازند. تغییر IP یا قطع کارت LAN، listener شبکه را می‌بندد؛ روی کارت جدید خودکار منتشر نمی‌شود. خاموش‌کردن LAN اتصال‌های remote و UDP relayهایشان را نیز می‌بندد.
- UDP ASSOCIATE به IP همان TCP client و پورت تثبیت‌شده وابسته است؛ relay روی همان IP محلی، با lifetime همان TCP session و سقف تعداد flow ساخته می‌شود.
- در صورت نیاز، firewall فقط برای ورودی TCP پورت انتخابی و UDP relayهای محدود، روی کارت انتخابی، LocalSubnet و Private profile تنظیم می‌شود؛ مالکیت و حذف ruleها مشخص است. policy عمومی و outbound تغییر نمی‌کند. تنظیم LAN پس از reconnect همان worker اعمال می‌شود.
- وضعیت‌ها: خاموش، در حال احراز هویت، آماده، در حال بازیابی، خطا. آدرس فعال فقط وقتی listener و تونل آماده‌اند نمایش داده می‌شود.
- در حالت SOCKS، کیل‌سوئیچ سراسری و gaming/routing سیستم اعمال نمی‌شوند؛ گزینه‌های ناسازگار توضیح روشن دارند. بسته‌شدن تونل با fail-closed داخلی پروکسی مدیریت می‌شود.

## منابع و خطا

صف‌ها، bufferها، DNS requestها و تعداد client/UDP flow سقف دارند؛ handshake، connect و idle timeout تعریف می‌شود. قطع یک client منابع همان client را آزاد می‌کند. مصرف پهنای باند پروکسی می‌تواند روی پینگ بازی اثر بگذارد؛ محدودکننده پهنای باند پروکسی در خود worker قابل افزودن است و نباید تنظیم TCP یا QoS کل سیستم را عوض کند.

## ترتیب اجرا

1. نمونه فنی packet-I/O روی Windows و یک اتصال TCP با IP عددی از پشته داخلی از طریق سرور واقعی؛ بدون ساخت آداپتور و بدون script. در صورت شکست، طراحی به TUN تغییر نمی‌کند و ابتدا مانع هسته حل می‌شود.
2. SOCKS محلی همراه DNS داخل تونل، TCP/UDP، محدودیت منابع و reconnect مستقل.
3. کنترل حالت در UI، تنظیمات، credential handling، ترجمه فارسی و گزارش وضعیت.
4. listener LAN، احراز هویت، محدودیت subnet، firewall ورودی و تغییرات آداپتور.
5. بسته‌بندی runtime و آزمون واقعی عدم اختلال؛ سپس عرضه به‌عنوان قابلیت آماده.

## معیار پذیرش

- snapshot مقایسه routeهای IPv4/IPv6، DNS، system proxy، MTU فیزیکی و policy عمومی firewall در startup/connect/disconnect/reconnect/crash هیچ تغییر ناشی از SOCKS نشان ندهد؛ فقط rule ورودی LAN اختیاری مجاز است.
- TCP طولانی و UDP پیوسته مستقیم با timestamp/sequence قبل و حین اتصال SOCKS برقرار باشند؛ destination و route بازی مستقیم تغییر نکنند. تست با IP عددی و نام دامنه و بازی واقعی انجام شود.
- مقصد یکسان همزمان از مسیر مستقیم و SOCKS آزمایش شود؛ IP خروجی پروکسی مربوط به VPN و مسیر مستقیم ثابت بماند. هر دو خانواده IP در صورت پشتیبانی آزمایش شوند.
- packet capture نشان دهد DNS مقصد SOCKS و payload آن روی کارت فیزیکی به‌صورت مستقیم خارج نمی‌شوند؛ فقط transport رمز‌شده سرور VPN مجاز است.
- قطع transport، شکست احراز هویت، timeout، crash worker، sleep/resume، تغییر شبکه و اشغال پورت مستقیم‌ها را از طرف برنامه تغییر ندهند و هیچ fallback مستقیم برای SOCKS ایجاد نکنند.
- LAN خاموش: از دستگاه دوم دسترسی وجود ندارد. LAN روشن: credential درست روی subnet مجاز کار می‌کند، رمز غلط و peer غیرمجاز رد می‌شوند. خاموش‌کردن LAN نشست‌های remote را می‌بندد.
- نتیجه آزمون‌ها اندازه‌گیری و ثبت شود؛ تضمین قطع‌نشدن ناشی از ISP، سرور بازی یا ازدحام پهنای باند داده نمی‌شود.
